# سامانه مدیریت پروژه و تحلیل عملکرد ترمینال‌های پوز

وضعیت: **کامل (فاز ۰ تا ۵)** — API، Worker، فرانت‌اند (React + Ant Design RTL + ECharts)، مستندات استقرار.
راهنمای استقرار (PM2/NSSM، Nginx، بکاپ، آرشیو پارتیشن): [`docs/deployment.md`](docs/deployment.md) · راهنمای مقیاس‌پذیری: [`docs/scaling.md`](docs/scaling.md).

## پیش‌نیاز
- Node.js LTS ≥ 20.11 (پیشنهاد 22)
- PostgreSQL 16+ (نصب مستقیم، بدون Docker)

### ساخت دیتابیس (یک‌بار)
```sql
CREATE ROLE pos_app LOGIN PASSWORD 'change_me';
CREATE DATABASE pos_support OWNER pos_app;
CREATE DATABASE pos_support_test OWNER pos_app;   -- فقط برای تست‌های دیتابیس‌دار
```
افزونه‌های `pg_trgm` و `btree_gist` «trusted» هستند و مالک دیتابیس می‌تواند بسازد.

## قرارداد مهاجرت‌ها
- زنجیره‌ی واحد `migrations/NNNN_name.sql`، اجرا با `scripts/migrate.ts`.
- هر فایل در یک transaction؛ checksum ثبت می‌شود و **تغییر فایل اعمال‌شده خطا می‌دهد**. تغییر جدید = فایل جدید.
- `packages/core/src/db/schema` آینه‌ی TypeScript جدول‌های معمولی است؛ منبع حقیقت، فایل‌های SQL است.

### قواعد تعویض پشتیبان/مسیر/بانک
- `POST /api/v1/terminals/:id/assignments` با `effectiveDate` اختیاری (پیش‌فرض: امروز به وقت تهران).
- تاریخ آینده مجاز نیست. تاریخ قبل از شروع ردیف جاری تاریخچه مجاز نیست (۴۰۹ `EFFECTIVE_BEFORE_START`).
- اگر تاریخ دقیقاً برابر شروع ردیف جاری باشد، همان ردیف اصلاح می‌شود.
- بازمحاسبه‌ی آمار در جدول `recompute_outbox` (همان transaction) ثبت می‌شود؛ Worker در فاز ۲ آن را مصرف می‌کند.

### جستجوی فارسی و pg_trgm
جستجو با `ILIKE '%…%'` روی `search_norm` انجام می‌شود و **همیشه درست** کار می‌کند. سرعت آن برای ۲۰۰ هزار ترمینال
به ایندکس trigram وابسته است که برای حروف فارسی به locale دیتابیس نیاز دارد. بررسی:
```sql
SELECT show_trgm('فروشگاه');   -- اگر خالی ({}) بود، دیتابیس با locale «C» ساخته شده
```
در آن صورت دیتابیس را با locale یونیکد بسازید (لینوکس: `en_US.UTF-8`؛ ویندوز: `English_United States.1252` کافی نیست،
از ICU استفاده کنید: `CREATE DATABASE pos_support LOCALE_PROVIDER icu ICU_LOCALE 'fa-IR' TEMPLATE template0;`).

## فاز ۲: ایمپورت
```bash
npm install                 # وابستگی‌های جدید: exceljs، pg-boss، pg-copy-streams، @fastify/multipart
npm run db:migrate          # 0004_imports.sql
npm run db:seed-periods
npm run dev:api             # ترمینال ۱
npm run dev:worker          # ترمینال ۲ (بدون Worker هیچ ایمپورتی پردازش نمی‌شود)
```
کاربر دیتابیس باید بتواند schema بسازد (pg-boss خودش schema `pgboss` را می‌سازد؛ مالک دیتابیس کافی است).

### جریان
1. `POST /api/v1/imports` (multipart؛ **فیلدهای `type` و `options` قبل از فایل**) ← فایل stream می‌شود، sha256 گرفته می‌شود،
   هدر خوانده و با پروفایل دفتر ← قالب رسمی مرکزی ← پیشنهاد خودکار تطبیق داده می‌شود.
2. اگر پروفایل/قالب رسمی کامل منطبق بود، اعتبارسنجی خودکار صف می‌شود؛ وگرنه وضعیت `needs_mapping` و
   `POST /imports/:id/mapping` (اختیاری: `saveProfileName` برای ذخیره‌ی پروفایل دفتر).
3. Worker: فایل ← `COPY` به staging ← اعتبارسنجی set-based ← وضعیت `validated`
   (`GET /imports/:id`، `/preview`، `/errors`، `/errors.xlsx`، `/unknown-terminals`).
4. `POST /imports/:id/commit {"mode":"strict"|"skip_invalid"}` ← Worker: merge در یک transaction.

`options` (JSON): `headerRow`، `calendar` (auto|jalali|gregorian)، `asOfDate` (تاریخ فایل تراکنش وقتی ستون ندارد)،
`effectiveDate` (تاریخ اعمال تعویض پشتیبان در ایمپورت ترمینال؛ پیش‌فرض امروز)، `source=monthly` + `periodId` (فایل پایان ماه).

### قواعد
- **ترمینال:** کلید «شماره ترمینال»؛ سلول خالی = بدون تغییر (با ایمپورت نمی‌توان مقدار را خالی کرد). ترمینال جدید پشتیبان لازم دارد.
  پشتیبان/مسیر/بانک با نام (نرمال‌شده‌ی ی/ک/ارقام) تطبیق داده می‌شود. نام تعریف‌نشده یا چندمعنایی = خطای همان ردیف.
- **تراکنش:** مانده‌ی تجمعی از ابتدای ماه شمسی. ترمینال تعریف‌نشده **خطا نیست**؛ کنار گذاشته و در `unknown-terminals` گزارش می‌شود.
  ردیف‌هایی که مانده‌ی تجمعی را با رکوردهای قبل/بعد همان ماه (در فایل یا دیتابیس) ناسازگار می‌کنند رد می‌شوند (`CUM_NON_MONOTONIC`).
- **ایدمپوتنت:** ایمپورت دوباره‌ی همان داده، ردیفی تغییر نمی‌دهد (`unchanged_rows`) و `import_batch_affected` خالی می‌ماند.
- شماره‌ی ردیف در گزارش خطا همان شماره‌ی ردیف اکسل است. سلول «شماره ترمینال» در اکسل باید **متن** باشد (قالب پیش‌فرض این‌طور ساخته می‌شود)؛
  عددِ خام قابل بازیابی صفر اول نیست.

### ستاد مرکزی (`system_admin`)
`POST /system/templates` (فایل نمونه) ← پیش‌نویس غیرفعال با نگاشت پیشنهادی ← بازبینی ← `PATCH /system/templates/:id {"isActive":true}`.
دفترها قالب را با `GET /imports/templates/:type` دانلود می‌کنند (بدون قالب مرکزی، قالب پیش‌فرض ساخته می‌شود).

## فاز ۳: تجمیع آماری
```bash
npm run db:migrate          # 0005_aggregation.sql
npm run dev:worker          # تجمیع فقط در Worker انجام می‌شود
```
**داده‌ی موجود از فاز ۲:** یک‌بار `POST /api/v1/admin/aggregates/rebuild` (مدیر دفتر) بزنید تا `fact_terminal_month` و `agg_*`
از روی snapshotهای موجود ساخته شوند. از آن به بعد هر ایمپورت و هر تعویض پشتیبان خودکار و افزایشی تجمیع می‌شود.

### مدل
| جدول | محتوا |
|---|---|
| `fact_terminal_month` | ترمینال × ماه شمسی: مبلغ/تعداد (آخرین مانده‌ی تجمعی ماه)، کامل/ناقص، طبقه، و **snapshot** پشتیبان/ستاد/مسیر/بانک همان ماه |
| `agg_supporter_month` / `agg_unit_month` / `agg_office_month` | تجمیع از fact (مبلغ، تعداد، شمارش دستگاه به تفکیک طبقه، تعداد ناقص) |
| `activity_rules` | آستانه‌ی «فعال» به‌ازای هر بانک (`bank_id=0` = پیش‌فرض دفتر) و دوره‌ی شروع اعتبار |
| `terminal_alerts` | افت بیش از `drop_alert_threshold_pct` نسبت به میانگین ۳ ماه کامل قبل (فقط ماه کامل، غیربرگشتی) |

### قواعد
- **طبقه‌ی ماهانه:** ۱ فعال (مبلغ ≥ آستانه)، ۲ کم‌تراکنش، ۳ برگشتی (انصراف تا پایان این ماه؛ بعد از ماه انصراف ردیفی ساخته نمی‌شود)،
  ۴ نوپا (نصب در همین ماه و در روز `new_terminal_cutoff_day` (پیش‌فرض ۲۰) یا بعد از آن؛ از ماه بعد عادی سنجیده می‌شود).
  تابع خالص `classifyActivity` (packages/shared) و SQL هم‌ارزند و تست می‌شوند.
- **آستانه:** آخرین قانون مخصوص بانک (valid_from ≤ ماه)؛ وگرنه قانون پیش‌فرض؛ وگرنه ۰.
- **پشتیبان آن ماه:** پشتیبان معتبر در min(آخرین روز ماه، امروز). تغییر در وسط ماه ← آمار همان ماه و بعدش برای پشتیبان جدید،
  ماه‌های قبل دست‌نخورده.
- **ماه ناقص** (آخرین فایل در آخرین روز ماه نیست): `is_complete=false` و در هشدار افت شرکت نمی‌کند.
- **ردیف صفر:** ترمینال موجه بدون فایل در ماه، ردیف با مبلغ ۰ می‌گیرد (برای شمارش کم‌تراکنش‌ها). فقط برای ماه جاری و ماه‌هایی که
  دفتر برایشان داده دارد ساخته می‌شود؛ ماه‌های بدون هیچ داده ردیف ندارند.
- **ایدمپوتنت:** هر مرحله «بازمحاسبه‌ی کامل slice از منبع» است؛ اجرای دوباره چیزی تغییر نمی‌دهد (`computed_at` فقط برای ردیف تغییرکرده عوض می‌شود).

### Jobها (Worker)
`aggregate.office` (کلیدهای دسته‌ی ایمپورت + outbox) · `activity.reclassify` (تغییر آستانه/تنظیمات) · `aggregate.rebuild` ·
`period.rollover` (روزانه ۰۰:۱۵ تهران) · `aggregate.sweep` (هر ۵ دقیقه؛ شبکه‌ی ایمنی برای کار معوق).
با Worker فعال، دسته‌ی ایمپورت بعد از merge در وضعیت `aggregating` می‌ماند تا job تجمیع آن را `completed` کند.

### API
`GET/PUT /settings/office` (روز نوپا، روز هشدار مقدماتی، درصد افت) · `GET/PUT /settings/activity-rules` ·
`POST /admin/aggregates/rebuild` · `GET /admin/aggregates/status`. تغییر آستانه/روز نوپا/درصد افت، بازطبقه‌بندی را صف می‌کند.

### Projection ماه ناقص
- ماه ناقص = آخرین فایل در آخرین روز ماه نیست. پوشش: `روز آخرین فایل - اول ماه + ۱`.
- **منحنی:** `month_progress_curve` (سهم تجمیعی مبلغ تا روز k، میانه‌ی حداکثر ۶ ماه کامل اخیر که حداقل ۲ فایل داخل ماه دارند؛ هفتگی و بعد از rebuild
  در Worker). اگر منحنی باشد و سهم تا آن روز ≥ ۵٪ باشد: `مبلغ / سهم`؛ وگرنه خطی: `مبلغ × روزهای ماه / روز پوشش`.
- منحنی در سطح دفتر است؛ برای فیلتر پشتیبان/ستاد همان ضریب اعمال می‌شود (تقریب).

### کش
نتیجه‌ی آماری با کلید `(endpoint، فیلترها، نقش و دامنه، data_version)` در جدول UNLOGGED `stats_cache` ذخیره می‌شود (پشت `CacheProvider`؛ قابل جایگزینی با Redis).
هر ایمپورت، تجمیع، بازطبقه‌بندی و تغییر تنظیمات `offices.data_version` را زیاد می‌کند و کش قبلی خودبه‌خود کنار می‌رود؛ housekeeping نسخه‌های قدیمی را پاک می‌کند.

### تست بار و گزارش EXPLAIN
```bash
npm run seed -- --size=large                  # ۲۰۰٬۰۰۰ ترمینال، ۵۰۰ پشتیبان، ۱۲ ماه (چند دقیقه)
```

اهداف: داشبورد/KPI زیر ۱ ثانیه، drill-down زیر ۲ ثانیه. اگر endpoint از هدف کندتر باشد، کد خروج ۲ است و پلان آن در گزارش هست.
قبل از تست بار تنظیمات `postgresql.conf` (حداقل `shared_buffers`، `work_mem`، `effective_cache_size`) را متناسب با RAM بگذارید.

### مدیریت پروژه
پروژه = مجموعه‌ای از ترمینال‌ها با بازه‌ی زمانی (شروع تا سررسید). وضعیت هر ترمینال: `not_started` · `in_progress` · `done` · `failed`.
**دامنه‌ی نقش:** مدیر دفتر/ادمین داده پروژه می‌سازند و ترمینال اضافه/حذف می‌کنند؛ مسئول ستاد و پشتیبان وضعیت ترمینال‌های داخل دامنه‌ی خودشان را عوض می‌کنند (عملیات گروهی «همه یا هیچ» است).
آمار هر نقش فقط ترمینال‌های داخل دامنه‌ی خودش را می‌شمارد.

| مسیر | توضیح |
|---|---|
| `GET/POST /projects` · `GET/PATCH /projects/:id` | فهرست (با پیشرفت و وضعیت زمان‌بندی) · ساخت · ویرایش/بستن |
| `POST /projects/:id/terminals` | افزودن با `terminalIds` یا `terminalNos` (حداکثر ۵۰۰۰)؛ ناشناخته‌ها گزارش می‌شوند |
| `POST /projects/:id/terminals/import` | اکسل/CSV (multipart؛ فیلد `type=project_terminals` **قبل از** فایل). ستون‌ها: «شماره ترمینال» (الزامی)، «وضعیت»، «توضیح» |
| `POST /projects/:id/terminals/remove` | حذف ترمینال‌ها از پروژه |
| `PATCH /projects/:id/terminals/:terminalId` · `POST /projects/:id/terminals/status` | تغییر وضعیت تکی · گروهی (+ تاریخچه در `project_terminal_events`) |
| `GET /projects/:id/terminals` · `/export` | فهرست با cursor و فیلتر · خروجی اکسل |
| `GET /projects/:id/progress` | قیف (کل ← شروع‌شده ← انجام‌شده) و پیشرفت به تفکیک پشتیبان |
| `GET /projects/:id/trend` | روند پیشرفت هر پشتیبان در گذر زمان (درصد ترمینال‌های بسته‌شده، ≤۲۰ نقطه) در برابر خط برنامه؛ از رویدادهای تغییر وضعیت ساخته می‌شود |
| `GET /projects/matrix` · `GET /projects/alerts` | ماتریس پروژه × پشتیبان · هشدار عقب‌افتادگی |

**هشدار عقب‌افتادگی** (`projectLag`، `packages/shared/src/projects.ts`): پیشرفت مورد انتظار = سهم زمان گذشته از بازه‌ی پروژه (خط برنامه‌ی خطی)؛ پیشرفت واقعی = (انجام‌شده + ناموفق) / کل.
شکاف > ۱۰ واحد درصد: «در معرض عقب‌افتادگی»، > ۲۰: «عقب‌افتاده»، بعد از سررسید با کار باقی‌مانده: «گذشته از سررسید».

### پیش‌بینی
Holt (روند میرا) و Holt-Winters جمع‌شونده (فصل ۱۲ماهه، حداقل ۲۵ ماه) در `packages/shared/src/forecast.ts`؛ مدل با **holdout سه‌ماهه‌ی آخر** (کمترین MAPE) انتخاب و روی کل سری دوباره برازش می‌شود. «میانگین» مدل پایه‌ی سری‌های کوتاه/پرنوسان است.
- فقط **ماه‌های کامل** استفاده می‌شود؛ ماه ناقص وسط سری درون‌یابی می‌شود. حداقل ۴ ماه کامل لازم است. پشتیبان/ستادی که ۳ ماه اخیر صفر بوده کنار می‌رود.
- بازه‌ی اطمینان ۹۵٪ تقریبی است (`±۱٫۹۶·σ·√h`)؛ فرض نرمال بودن خطا دارد و برای تصمیم‌های حساس «برآورد» تلقی شود.
- اجرا در Worker: هفتگی (یکشنبه ۰۴:۳۰ تهران، همه‌ی دفترها) یا با `POST /forecast/run` (مدیر دفتر). نتیجه در `forecast_results` (جایگزینی کامل دفتر در یک transaction) و وضعیت اجرا در `forecast_runs`.
- مسیرها: `GET /forecast?scope=office|unit|supporter&id=` · `GET /forecast/summary?scope=unit|supporter` · `GET /forecast/status` · `POST /forecast/run`.
  دامنه: مدیر همه‌ی سطح‌ها؛ مسئول ستاد ستاد و پشتیبان‌های خودش؛ پشتیبان فقط خودش.

### تکمیلات ترمینال
| مسیر | توضیح |
|---|---|
| `POST /terminals/:id/return` | ثبت انصراف (`returnedAt` پیش‌فرض امروز، نه آینده و نه قبل از نصب) + دلیل؛ آمار از ماه انصراف بازمحاسبه می‌شود |
| `POST /terminals/:id/reactivate` | لغو انصراف (ثبت اشتباه) |
| `POST /terminals/bulk/assign` | تعویض گروهی پشتیبان/مسیر/بانک (حداکثر ۱۰۰۰)؛ همه یا هیچ؛ خطای هر ترمینال در `details.failures` |
| `POST /supporters/:id/transfer-terminals` | انتقال همه‌ی ترمینال‌های یک پشتیبان (یا فهرست انتخابی) به پشتیبان دیگر |
| `POST /supporters/:id/transfer-unit` | انتقال پشتیبان به ستاد دیگر (فقط مدیر/ادمین داده) |

**انتقال پشتیبان بین ستادها:** از تاریخ اعمال به بعد ستاد ترمینال‌های او عوض می‌شود و ماه‌های قبل دست‌نخورده می‌ماند (ردیف تاریخچه‌ی جاری بسته و ردیف جدید باز می‌شود).
ردیف‌هایی که همان روز یا بعد از تاریخ اعمال شروع شده‌اند در همان‌جا اصلاح می‌شوند (`clamped` در پاسخ).

### فرانت‌اند (`apps/web`)
SPA فارسی RTL با Ant Design و ECharts: داشبورد (KPI، روند، سهم بانک، رشد، نقشه‌ی حرارتی، هشدارها)، ترمینال‌ها (جستجو، جزئیات، تاریخچه، انصراف، تعویض تکی/گروهی)،
پروژه‌ها (فهرست، ماتریس، هشدار، جزئیات، ایمپورت اکسل)، پیش‌بینی، ایمپورت (نگاشت ستون، اعتبارسنجی، تأیید)، مدیریت (ستاد/پشتیبان/انتقال، بانک/مسیر، تنظیمات، کاربران).
تاریخ‌ها شمسی نمایش داده و (با فرمت `۱۴۰۴/۰۵/۱۰`) دریافت می‌شوند؛ توکن در `localStorage` و تمدید خودکار با refresh token است.
منوها بر اساس نقش نمایش داده می‌شوند، ولی **مرز امنیتی همیشه API است** (دامنه‌ی نقش در Repository).
تولید: `npm run build:web` ← `apps/web/dist` (Nginx سرو می‌کند؛ [`deploy/nginx/pos-support.conf`](deploy/nginx/pos-support.conf)).

## فاز ۶: پروژه‌های خودکار، دو نوع مبلغ، همگام‌سازی فایل تراکنش، امتیاز پشتیبان

مهاجرت `0008_automation_scoring.sql` را اعمال کنید و بعد **یک‌بار** «بازسازی آمار تجمیعی» (مدیریت ← تنظیمات ← نگهداری) را بزنید تا ستون‌های «مبلغ کل» برای ماه‌های گذشته پر شوند.

### دو نوع مبلغ
- **مبلغ خرید** (`amount`): مجموع تراکنش‌های خرید که به حساب پذیرنده واریز شده؛ مبنای پیش‌فرض فعال/کم‌تراکنش، رشد و داشبوردها.
- **مبلغ کل** (`total_amount`): خرید + شارژ + قبض و ...؛ ستون اختیاری فایل تراکنش (اگر نباشد، برابر مبلغ خرید فرض می‌شود).
- در «مدیریت ← تنظیمات ← مبنای مبلغ» مشخص می‌شود طبقه‌بندی (فعال/کم‌تراکنش) و پروژه‌های فاقد درآمد بر پایه‌ی کدام مبلغ باشد (`office_settings.income_basis`). تغییر آن بازطبقه‌بندی می‌کند.

### پروژه‌های خودکار «فاقد درآمد» (`projects/auto.ts`)
| نوع | چه ترمینال‌هایی | مهلت | شرط ساخت |
|---|---|---|---|
| `no_income_prev` | کم‌تراکنش‌های **ماه قبل** | روز `auto_prev_deadline_day` (پیش‌فرض ۲۰) ماه جاری | داده‌ی ماه قبل دست‌کم ۵۰٪ کامل باشد |
| `no_income_curr` | کم‌تراکنش‌های **ماه جاری** | آخرین روز همان ماه | از روز `auto_curr_check_day` (پیش‌فرض ۲۰) و فایل تراکنش تا روز قبلش ایمپورت شده باشد |

- «کم‌تراکنش» = طبقه‌ی ۲ در `fact_terminal_month` (آستانه‌ی بانک؛ نوپا و برگشتی خارج‌اند).
- هر نوع در تنظیمات قابل فعال/غیرفعال است و دکمه‌ی «ایجاد/به‌روزرسانی» دارد؛ آخرین اجراها در `auto_project_runs` ثبت و در تنظیمات نمایش داده می‌شود.
- Job `project.auto` هر ۴ ساعت اجرا می‌شود و ایدمپوتنت است (فقط ترمینال‌های جدید را اضافه می‌کند). پروژه‌ی بسته/لغوشده بازنمی‌شود و ترمینالی که دستی از پروژه‌ی خودکار حذف شود (`auto_project_exclusions`) دوباره اضافه نمی‌شود. ترمینالی که بعداً از آستانه عبور کند خودکار «انجام‌شده» نمی‌شود.

### همگام‌سازی اطلاعات ترمینال با فایل تراکنش
ستون‌های اختیاری جدید فایل تراکنش: `total_amount`، `total_tx_count`، `shop_name`، `owner_name`، `phone`، `address`، `bank_name` (حتی پروفایل/قالب رسمی قدیمی، اگر عنوان این ستون‌ها در فایل باشد، خودکار نگاشت می‌شوند).
- مغایرت با دیتابیس ⇒ به‌روزرسانی ترمینال؛ سلول خالی چیزی را پاک نمی‌کند. فایلِ قدیمی‌تر از آخرین فایل همگام‌شده‌ی ترمینال (`terminals.info_as_of`) بازنویسی نمی‌کند.
- هر تغییر در `audit_log` با **کاربر، زمان، شناسه/نام فایل و مقدار قبل/بعد** ثبت و در پنجره‌ی ترمینال («تاریخچه‌ی تغییرات») نمایش داده می‌شود. تغییر بانک در تاریخچه‌ی تخصیص (SCD2) با تاریخ فایل ثبت می‌شود و «ثبت‌کننده/زمان ثبت» دارد.
- بانکِ ناشناخته طبق تنظیم `sync_create_banks` ساخته می‌شود. کل همگام‌سازی با `sync_terminal_info` قابل خاموش‌کردن است.
- **ترمینال‌های تعریف‌نشده**: ترمینال‌های موجود در فایل که در دیتابیس نیستند بعد از ثبت وارد `pending_terminals` (به‌همراه ردیف‌های تراکنششان) می‌شوند. صفحه‌ی «تعریف‌نشده‌ها» (نشان تعداد کنار منو) امکان تعیین پشتیبان/مسیر/بانک گروهی یا «نادیده‌گرفتن» دارد؛ با تعیین پشتیبان، ترمینال با اطلاعات فایل ساخته می‌شود و تراکنش‌هایش وارد آمار می‌گردد (حتی ماه‌های قبل). ساخت دستی یا ایمپورت ترمینال هم همین ردیف‌ها را جذب می‌کند.

### امتیاز پشتیبان (`/scores`، `GET /analytics/supporter-scores`)
امتیاز هر ماه (۰–۱۰۰) = میانگین وزنی چهار مؤلفه؛ امتیاز کلی = میانگین ماه‌های **کامل** بازه (۳/۶/۱۲ ماه)؛ ماه ناقص لحاظ نمی‌شود.
- رشد مبلغ خرید و رشد تعداد تراکنش نسبت به ماه قبل (۰٪ = ۵۰، +۲۵٪ = ۱۰۰، −۲۵٪ = ۰).
- دستگاه‌ها: نصف رشد دستگاه فعال + نصف سهم دستگاه‌های فعال از قابل‌سنجش.
- پروژه‌ها: برای همه‌ی پروژه‌های هم‌پوشان با ماه، نسبت پیشرفت واقعی (از تاریخچه‌ی رویدادها تا پایان ماه) به پیشرفت مورد انتظار خط برنامه، میانگین وزنی به تعداد ترمینال.
- مؤلفه‌ی بدون داده حذف و وزنش بین بقیه پخش می‌شود. وزن‌ها (پیش‌فرض ۳۰/۱۵/۲۰/۳۵) در تنظیمات قابل تغییرند. صفحه شامل رتبه‌بندی، روند ماهانه، رادار مؤلفه‌ها، جدول پروژه‌ها و توضیح متنی هر ماه است. دسترسی بر پایه‌ی نقش (پشتیبان فقط خودش، سرپرست ستاد فقط ستاد خودش).

## فاز ۷: سطح دسترسی کاربران، ثبت گروهی بانک/مسیر، جستجو و ویرایش گروهی ترمینال

مهاجرت `0009_access_levels.sql` را اعمال کنید (`npm run db:migrate`) و API را ریستارت کنید.

### سطح دسترسی (مجوزها)
- **نقش** دامنه‌ی داده را تعیین می‌کند (کل دفتر / یک ستاد / یک پشتیبان)؛ **مجوز** تعیین می‌کند کاربر چه کارهایی بتواند بکند (`packages/shared/src/permissions.ts`: داشبورد، امتیاز، پیش‌بینی، خروجی اکسل، ویرایش ترمینال، تاریخچه‌ی تغییرات، تعریف‌نشده‌ها، ایمپورت، ستاد/پشتیبان/بانک/مسیر، پروژه، تنظیمات، نگهداری، کاربران).
- پیش‌فرض هر نقش دقیقاً رفتار قبلی است و **سقف** همان نقش هم هست: مدیر دفتر می‌تواند برای هر کاربر مجوز **کم** کند («فقط مشاهده»، «فقط گزارش‌ها»، یا انتخاب دستی) ولی بیشتر از سقف نقش نمی‌تواند بدهد. مدیر دفتر همیشه همه‌ی مجوزها را دارد و قابل محدودسازی نیست.
- مدیریت ← کاربران و سطح دسترسی ← «ویرایش». ذخیره در `users.permissions` (`NULL` = پیش‌فرض نقش) و در `audit_log` ثبت می‌شود.
- اعمال در API: `requirePermission(...)` به‌جای `requireRoles` روی مسیرها؛ مجوز از دیتابیس خوانده می‌شود (نه JWT) و تا ۱۵ ثانیه کش دارد، پس تغییر بدون ورود مجدد (در همان پروسه فوراً) اعمال می‌شود. منوها و دکمه‌های فرانت هم با `can('...')` پنهان می‌شوند؛ مرجع نهایی همیشه API است.

### ثبت گروهی بانک و مسیر
مدیریت ← بانک و مسیر ← «افزودن گروهی»: فهرست را (مثلاً ستونی از اکسل) می‌چسبانید؛ پیش‌نمایش موارد جدید/تکراری نشان داده می‌شود. برای بانک می‌توان بعد از نام، با Tab یا «؛» کد را هم نوشت. تکراری‌ها (با نرمال‌سازی ی/ک/ارقام) رد می‌شوند. API: `POST /banks/bulk`، `POST /route-groups/bulk` (حداکثر ۵۰۰/۱۰۰۰ مورد، همه یا هیچ، با audit).

### جستجو و ویرایش گروهی ترمینال
ترمینال‌ها ← «جستجوی گروهی»: چند شماره (هر خط/فاصله/کاما) را می‌چسبانید؛ پیداشده‌ها در جدول و ناموجودها جداگانه (با دکمه‌ی کپی) نشان داده می‌شوند. روی پیداشده‌ها «تعویض گروهی پشتیبان/مسیر/بانک» (همان ویرایش گروهی موجود، همه یا هیچ و با تاریخچه) یا باز کردن تک‌ترمینال ممکن است. API: `POST /terminals/lookup` (حداکثر ۵۰۰۰ شماره؛ فقط در دامنه‌ی دسترسی کاربر، شماره‌ی خارج از دامنه هم «ناموجود» گزارش می‌شود تا وجودش افشا نشود).

## ورود و داده‌ی نمایشی
**ورود فقط با نام کاربری و رمز است.** «کد دفتر» اختیاری است و فقط اگر همان نام کاربری در چند دفتر وجود داشته باشد (پاسخ `409 OFFICE_REQUIRED`) از کاربر پرسیده می‌شود.

داده‌ی نمایشی واقع‌نما (۴ ستاد، ۱۶ پشتیبان، ۶ بانک، ۱۲ مسیر، ۶۴۰ ترمینال با نام فارسی، ۱۴ ماه تراکنش با روند و فصل‌بندی، ۴ پروژه و کاربران آماده):
```bash
npm run db:migrate && npm run db:seed-periods
npm run seed:demo              # دفتر «demo»؛ برای ساخت دوباره:  npm run seed:demo -- --reset
```
گزینه‌ها: `--terminals=640` · `--months=14` · `--password=demo1234` · `--office=demo`. خروجی شامل تجمیع آمار و پیش‌بینی هم هست و بعد از اجرا داشبورد پر است.
کاربران (رمز همه `demo1234`): `admin` مدیر دفتر · `data` ادمین داده · `head1`..`head4` مسئول ستاد · `sup1`..`sup16` پشتیبان.
داده‌ی بار (۲۰۰ هزار ترمینال) جداست: `npm run seed -- --size=large`.

### رابط کاربری: انتخاب تاریخ، افزودن از فهرست، داشبورد
- **تاریخ شمسی:** همه‌ی فیلدهای تاریخ با `react-multi-date-picker` (تقویم شمسی، ارقام و ماه‌های فارسی، شروع هفته از شنبه) کار می‌کنند؛ مقدار بیرونی همیشه ISO میلادی است (`apps/web/src/components/JalaliDateField.tsx`).
- **افزودن ترمینال به پروژه:** از «افزودن از فهرست ترمینال‌ها» (جستجو و فیلتر ستاد/پشتیبان/بانک/مسیر، انتخاب بین چند صفحه یا «انتخاب همه‌ی نتایج فیلتر»، حداکثر ۵۰۰۰)، با شماره، یا با اکسل.
- **داشبورد ← روند ۱۲ ماهه:** شاخص (مبلغ / تراکنش / ترمینال فعال) و تفکیک (کل / بانک‌ها / پشتیبان‌ها) قابل انتخاب است؛ در حالت تفکیک چند مورد هم‌زمان مقایسه می‌شود (پیش‌فرض ۵ مورد برتر).
- **داشبورد ← پیشرفت پروژه‌ها:** انتخاب پروژه، روند پیشرفت هر پشتیبان در برابر خط برنامه، و وضعیت فعلی ترمینال‌ها به تفکیک پشتیبان.
