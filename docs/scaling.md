# راهنمای مقیاس‌پذیری

اهداف طراحی: ۲۰۰ هزار ترمینال، ۵۰۰ پشتیبان، فایل روزانه تا ۱٫۱ میلیون ردیف، داشبورد زیر ۱ ثانیه. یک سرور متوسط (۸ هسته، ۳۲ گیگ، SSD) کافی است.
قبل از هر تغییر، با `npm run perf:explain` گزارش را بگیرید و گلوگاه واقعی را پیدا کنید.

## ترتیب پیشنهادی (از ارزان به گران)
1. **تنظیم PostgreSQL** — `shared_buffers`، `work_mem`، `effective_cache_size`، `max_wal_size` (راهنمای استقرار). بیشترین اثر را معمولاً همین دارد.
2. **VACUUM/ANALYZE** — بعد از ایمپورت بزرگ خودکار اجرا می‌شود (`IMPORT_VACUUM_THRESHOLD`). اگر برنامه‌ی کوئری‌ها بد شد: `ANALYZE` دستی روی `fact_terminal_month` و `agg_*`.
3. **آرشیو پارتیشن‌های قدیمی** — `npm run db:archive` (راهنمای استقرار §۷) تا جدول‌ها و کش حافظه کوچک بمانند.
4. **چند پروسه‌ی API** — API بی‌وضعیت است؛ چند نمونه روی پورت‌های جدا (`API_PORT=3001`، …) و `server` های بیشتر در `upstream pos_api` (Nginx). هر نمونه `DB_WRITE_POOL_MAX`/`DB_READ_POOL_MAX` جداگانه دارد؛ مجموع همه‌ی اتصال‌ها را زیر `max_connections` نگه دارید (یا PgBouncer در حالت transaction pooling برای pool خواندن/نوشتن API؛ اتصال Worker و مهاجرت‌ها را مستقیم به PostgreSQL نگه دارید).
5. **Read replica** — `READ_DATABASE_URL` را به replica بدهید؛ همه‌ی GETهای داشبورد و گزارش از آن می‌خوانند (`DB_READ_STATEMENT_TIMEOUT_MS` سقف کوئری را می‌گذارد). تأخیر replication در ماه‌های تازه‌ایمپورت‌شده ممکن است چند ثانیه دیده شود.
6. **Worker** — `WORKER_CONCURRENCY` برای jobهای سبک؛ ایمپورت/تجمیع عمداً ترتیبی‌اند (هر دفتر هم‌زمان یک تجمیع). Worker دوم روی ماشین جدا مجاز است (pg-boss کار را تقسیم می‌کند؛ زمان‌بندی‌ها تکراری اجرا نمی‌شوند).
7. **کش** — `stats_cache` (UNLOGGED، در PostgreSQL) پشت `CacheProvider` است. اگر تعداد کاربران هم‌زمان زیاد شد، پیاده‌سازی Redis را جایگزین کنید (بدون تغییر در کد endpointها).
8. **Storage** — فعلاً دیسک محلی. برای چند سرور API، `STORAGE_LOCAL_PATH` باید روی مسیر مشترک (NFS/SMB) باشد، یا `StorageProvider` جدید (S3/MinIO) نوشته شود (رابط کوچک: `put/get/delete`).

## نشانه‌ها و اقدام
| نشانه | علت محتمل | اقدام |
|---|---|---|
| داشبورد کند شد | کش سرد/ماه جدید یا آمار قدیمی | `ANALYZE`؛ `perf:explain`؛ بررسی `slow query` در لاگ |
| ایمپورت بیش از ۲ دقیقه برای ۱ میلیون ردیف | دیسک/WAL/`work_mem` | `bench:import`؛ WAL روی SSD جدا؛ `max_wal_size` بیشتر |
| `timeout` در GET سنگین | کوئری بدون ایندکس مناسب | EXPLAIN همان endpoint؛ ایندکس/ستون تجمیعی |
| اتصال‌های دیتابیس تمام شد | چند پروسه × pool | pool را کم کنید یا PgBouncer |
| دیسک پر شد | snapshot/audit قدیمی، WAL | آرشیو پارتیشن؛ بررسی `archive_command` |

## چیزهایی که عمداً ساده مانده
- جداسازی ستاد/دفتر با `office_id` در همه‌ی جدول‌هاست؛ اگر روزی دفترها خیلی بزرگ شدند، پارتیشن‌بندی بر اساس دفتر یا دیتابیس جدا برای دفترهای بزرگ ممکن است (مرز ماژول‌ها همین را اجازه می‌دهد).
- پیش‌بینی روی سری‌های ماهانه‌ی تجمیعی انجام می‌شود (چند هزار سری، ثانیه‌ها)؛ نیازی به scale جدا ندارد.
